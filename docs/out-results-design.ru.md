# `out`: принятое решение L7

Статус: владелец выбрал вариант A — публикация выходов только при успехе.
Решение подтверждено сообщением «делаем А» 19 сентября 2026. Реализован начальный контракт: синхронные функции R, unborrowed payload.
[Отчёт и проверки](out-a-validation-2026-09-19.ru.md).
Связанный этап: [L7](language-completeness-roadmap.ru.md#l7-обязательное-использование-результатов-и-out).

## Что уже разрешено

- Результаты функций значимы по умолчанию; `@discardable` явно разрешает игнорирование.
- Нельзя скрыть потерю результата присваиванием переменной, которую позже перезаписали.
- Выход через `out` создаёт такое же обязательство использования, как обычный результат.
- Обычный изменяемый указатель сам по себе не становится `out`.

## Решение: что видит вызывающая сторона после `throw`

### A. Публикация выходов только при успешном возврате

Все `out`-значения сначала создаются во временном хранилище функции. При обычном
возврате компилятор проверяет инициализацию каждого выхода и переносит значения в
назначения вызывающей стороны. Если назначение уже содержало значение, его обычное
уничтожение выполняется при замене.

При `throw` созданные временные значения уничтожаются, а назначения вызывающей стороны
сохраняют состояние до вызова. Новое обязательство использования не возникает.
Это касается только `out`: I/O и другие внешние эффекты функции не откатываются.

Плюсы: выход ведёт себя как возвращаемое значение; ошибка не публикует частичный набор
результатов. Минус: для крупных результатов могут потребоваться дополнительное временное
хранилище и перенос; их нужно включать в анализ стека и Move/borrow-контракты.

### B. Запись непосредственно в назначения

Присваивания через `out` сразу меняют назначения. При `throw` вызывающая сторона может
увидеть уже записанные значения. Нужно отдельно определить, какие выходы гарантированно
инициализированы на каждом исключительном пути, кому принадлежит их cleanup и когда
возникает обязательство использования частичного результата.

Плюсы: можно явно предоставлять частичный прогресс, меньше необходимости во временном
хранилище. Минусы: `out` становится сложнее обычного возвращаемого значения; обработчик
ошибки зависит от состояния каждого выхода. Уже инициализированные и новые назначения
требуют разных правил.

## Принятое направление

Вариант A принят для нового `out`; B сохранён выше только как рассмотренная альтернатива.
Для частичного прогресса использовать существующий изменяемый
borrow с явным контрактом функции или возвращаемый payload ошибки. Синтаксис объявления — `out T name`, вызова — `out place`;
нормативный контракт закреплён в Core R-FUNC-0022 (draft.48).

## Критерии проверки реализации

1. Все обычные возвраты инициализируют каждый выход; чтение до инициализации запрещено.
2. Несколько выходов не перекрываются между собой и конфликтующими входными borrow.
3. Copy/Move, ранний возврат, `throw`, `finally` и частичная инициализация дают ровно одну
   очистку каждого владельца.
4. Для каждого успешного выхода отслеживается конкретное полученное значение, включая
   перезапись, ветвления, циклы, передачу дальше и явное `as void`.
5. Callable, traits, generics и интерфейс модуля сохраняют режим и обязательства `out`.
6. Паника сохраняет действующий контракт завершения R; новый `out` не вводит unwinding.
