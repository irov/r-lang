# R: план расширения и завершения языка

Создан: 15 сентября 2026. Обновлён: 28 сентября 2026.
Статус: владелец разрешил реализацию указанного ниже объёма, включая уточнённый
автоматический compile-time. Реализация начата; незакрытые пункты не считаются готовыми.

## Реализация от 20 сентября: неявные ошибки main

Core — draft.50; Library — draft.19 (имена `std.bits::read_error` в общей диагностике).
Сохранены четыре существующие формы `i32 main`; явное `throws` запрещено.
Неявный набор содержит ровно 25 Copy-семейств R-FUNC-0008. Пользовательские ошибки,
`std.json::error` и владеющие `new_error`/`push_error`/`insert_error` требуют catch.

По решению владельца выбраны раздельные диапазоны статусов Darwin:

| Назначение | Статус |
|---|---|
| Успех / ошибки приложения | 0 / 1…111 |
| allocation | 112 |
| io, filesystem | 113 |
| network | 114 |
| conversion, format | 115 |
| async_runtime, threading | 116 |
| Остальные стандартные домены | 117 |
| Резерв подложки | 118…123 |
| Недопустимый результат main | 124 |
| Существующие ошибки запуска | 125…127 |

Генерируемая точка входа C17 выводит allocation-free диагностику (domain/name/code/native_code),
запрашивает отмену задач, выполняет полный drain, уничтожает thread_local/static-объекты
с промежуточными drain и завершает процесс нормально. Неизвестный carrier tag остаётся
внутренней проверкой целостности. Деструкторы могут создавать новую учитываемую работу.

Сам неявный throws ослабляет ограничения. Выбранное разделение статусов отдельно
ограничивает `main` диапазоном 0…111: иной i32 диагностируется во время завершения и
даёт 124 после обычной очистки. Неявные разрешения `main` не учитываются как
использование API примером.

Проверки и точные результаты: [отчёт](main-error-boundary-validation-2026-09-20.ru.md).

23 сентября `main` примеров и бенчмарков переведены на эту границу. Удалены catch-ветки
отказов среды: alloc → 71, start → 75, thread/barrier → 70, time/duration → 74/76,
I/O стандартных потоков и loopback-сети, а также служебные коды walkthrough-примеров.
Статусы, которые задают CLI-контракт примера и проверяются командными тестами, сохранены:
64, 65 для `parse_error`/`path_error`/`utf8_error`, 66 для файла пользователя,
69, 78 для `env_error`. Владеющие `push_error`/`insert_error` → 71, `std.json::error`
и пользовательские ошибки по-прежнему ловятся явно. README примеров описывают
статусы 112…117; фикстуры компилятора не менялись.

## Реализация от 23 сентября: развилка не передаётся и не возвращается

Core — draft.51 (475 правил, число не изменилось). R-EXPR-0014 запрещает conditional
expression `?:` на любой глубине внутри аргумента вызова (функции, метода, `format`,
awaited call, операнда `panic`, value operand standard type call) и внутри операнда
`return`, включая return в switch clause. Выбранное значение сначала именуется
(`T value = c ? a : b;`), либо развилка записывается через `if`. Нарушение —
`R-DIAG-FLOW-001` по одной диагностике на внешнюю развилку. Проверка идёт по AST до
разрешения имён (`compiler/semantic/conditional_positions.inc`).

Примеры и `library/r` переписаны в явный `if`; фикстуры компилятора — в именованный
локал, чтобы сохранить проверку слияния заимствований и Move-веток внутри `?:`.
Три фикстуры с развилкой в аргументе переформулированы так, что развилка именуется
до вызова. Инициализаторы, присваивания, условия и `match` не ограничены.

## Реализация от 23 сентября: L8 и L1.3

Core — draft.52 (475 правил). Явные generic-аргументы записываются как `name::<arguments>`
(выбор владельца): после имени функции, квалифицированного имени, `Owner<args>::name` и имени
метода в вызове через receiver. Список полный и в порядке заголовка: типы, проверенные
константы и наборы `throws(...)`, включая пустой. Он закрывает функцию без вывода; для
семейства перегрузок список и число аргументов выбирают ровно один generic-член.
Result-only определения разрешены (`@generic<T> array<T> make()` вызывается как
`make::<i32>()`), невыведенный параметр диагностируется в месте вызова.

Закрытое имя в позиции значения — function item (`auto parse = decode::<Header>;`).
`Owner::method` и `Owner<args>::method` без вызова дают function item с receiver первым
параметром (L1.3). Грамматика: `explicit-generic-arguments` в Annex A (278 продукций),
узел `generic_argument_list`. Примеры: json_tool (`canonical::<Configuration>`), generics,
methods; фикстуры `codegen_explicit_generics` и `codegen_async_explicit_generics`.

По решению владельца стиль единый: встроенные операции std с type operands тоже пишутся
через тот же список — `std.array::create::<T>()`, `std.array::with_capacity::<T>(n)`,
`std.dict::create::<K, V>()`, `std.sync::once_lock::<T>()`, `core::enum_count::<T>()`,
`core::enum_from_name::<T>(text)` и остальные из 18 форм. Старая запись `op(T, …)` — синтаксическая
ошибка с подсказкой. Library — draft.20. Переписано 684 вызова в примерах, библиотеке,
фикстурах, тестах и спецификациях. (Здесь уже показана запись после перехода на угловые
скобки, см. следующий раздел; в draft.52 список писался `name::(arguments)`.)

## Реализация от 23 сентября: угловые скобки

Core — draft.53 (475 правил), Library — draft.21. По решению владельца списки аргументов
типов пишутся в угловых скобках: `Box<i32>`, `array<u32>`,
`dict<i32, bool>`, `o<Color>`, `task<i32 throws Bad>`, `std.sync::once_lock<u32>`,
заголовок `@generic<T: copy, U: copy>`, ограничение-трейт `Read<T>`. В выражении список
вводится явной формой `::<...>`: `decode::<Header>(text)`, `std.array::create::<u32>()`,
`core::enum_from_name::<Color>(text)`, `auto parse = decode::<Header>;`,
`cell.convert::<u8>(7u8)`, `auto to_u8 = Cell<i32>::convert::<u8>;`. Путь владельца в
выражении — `Cell<i32>::create(...)`, литерал агрегата — `Box<i32> { .value = 1 }`.

Круглые скобки остаются там, где стоят значения или параметры: списки параметров, типы
`fn(...)`, `u8[N]`, наборы `throws(...)`, `opaque(...)`, `sizeof(T)`/`alignof(T)`,
инициализатор `new T(expr)` и payload вариантов `Owned(own i32*)`.

Правила разбора (R-TYPE-0031): `>>` закрывает два списка; константный аргумент,
содержащий `>` или `>>`, заключается в скобки (`Buffer<(N >> 1usize)>`); в выражении `Name<...>`
считается типом, только если парная `>` стоит перед `::` или `{`, иначе `<` — сравнение.
Прежний заголовок `@generic(...)` и `generic<...>` без `@` диагностируются с подсказкой.
Каноническое написание в диагностиках, reflection (`core::type_name`) и именах
инстансов тоже угловое: `array<example.reflection.model::Level>`, `grow<i32>`.

Переписано 3457 списков в 489 из 1206 R-файлов (по CST старого фронтенда, только
разделители); AST совпал для всех файлов, которые разбирались до перехода. Отдельно
переписаны R-фрагменты в строках тестов C/Python, генераторы фикстур ABI, реестр
стандартных типов, спецификации и документация.

## Реализация от 24 сентября: L9, композиция scoped tasks

Core — draft.60 (480 правил), interface schema 19 без изменений; новое правило R-STMT-0018.
Решения владельца: тайм-аут — `first_until`/`all_until` (только готовность, монотонное
`std.time::instant`); судьба проигравших явная — `cancel_all` + `all`, ничего не отменяется
само; оператор `select` добавлен (пункт B4 плана фундамента) с той же явной судьбой проигравших.

- **L9.1.** `await g.first_until(deadline, &a, &b)` → `o<usize>` (`none` — дедлайн раньше),
  `await g.all_until(deadline)` → `bool`. Как `first`/`all`, это барьеры готовности: ничего не
  потребляют, ошибок не наблюдают, займов не завершают. Дедлайн — `dispatch_after_f` в
  runtime (`r_runtime_task_scope_wait_until`); готовность проверяется раньше дедлайна.
  `select (g) { case T x = await move a: ... case await move b: ... case until (d): ... }`
  ждёт как `first_until` по участникам в порядке ветвей и выполняет ровно одну ветвь; ветвь
  выбранного участника потребляет его через `await move`, поэтому его ошибка
  распространяется из ветви.
- **L9.2.** Select и дедлайн никогда не отменяют. Остальные участники продолжают работу и
  держат слоты и займы; после select участник, потреблённый лишь на части путей, —
  select-pending: его нельзя назвать (`R-DIAG-MOVE-002`), а разрешают его только
  `g.cancel_all()` или выход из группы. `g.cancel_all()` запрашивает отмену всех
  непотреблённых участников и потребляет их наблюдения, но не ждёт: подтверждение наблюдают
  `await g.all()` или выход. Payload отменённого участника (и checked-ошибка) уничтожается
  один раз без наблюдения; отмена не доказывает отсутствия внешнего эффекта. Ошибки
  остальных участников наблюдаются их `await move` внутри ветвей.
- **L9.3.** Ограниченные ожидания, `cancel_all` и select не запускают задач и не занимают
  слотов; ёмкость и `scope_full`, сохранение Move/займов при отказе старта и путь отмены
  родителя — прежние из R-STMT-0017. Из одновременно готовых выбирается наименьший индекс
  аргумента или ветви. Наступивший дедлайн не меняет состояния участников, займов и Move.
- **L9.4.** `codegen_scoped_select`: таймер против вычисления (`first_until`, `all_until`),
  одновременная готовность (`first` и select выбирают первый аргумент/ветвь), ошибки двух
  детей (выбранная распространяется, payload другой уничтожается ровно один раз — счётчик
  drop), задержанное подтверждение отмены с однократным `finally` (двойной `cancel_all`,
  выход по дедлайну). `codegen_scoped_select_io`: таймер против UDP-приёма (дедлайн выигрывает,
  отмена освобождает займ буфера только после подтверждения backend, тот же сокет затем
  принимает датаграмму). Отрицательные случаи — `r_semantic_test_scoped_select`, синтаксис —
  `compositional_syntax_tests.inc`, проба `task_select` в аудите, пример
  [fanout](../examples/fanout/README.md) использует select с бюджетом.

Вне этапа: select по каналам и сигналам отмены (нужны библиотечные A2/A3 плана фундамента), динамический
набор участников (select в цикле по уже потреблённым), автоматическая отмена проигравших.

## Реализация от 24 сентября: L5, dyn-интерфейсы

Core — draft.59 (479 правил), interface schema 19. Решения владельца: набор реализаций —
типы, которые программа приводит к интерфейсу; запись `dyn(Store)*` как у `opaque(...)`;
приведение неявное по месту; синхронные и async-методы.

- **L5.1.** `dyn(Контракты)` — закрытый тип, существующий только за заимствованием:
  `dyn(Store)*`, `const dyn(Store & send)*`, nullable-формы (новое правило R-TYPE-0051).
  Контракты — traits, capabilities и равенства связанных типов; одинаковые контракты в любом
  порядке и модуле — один тип. Метод интерфейса принимает receiver `const Self*`/`Self*`, без
  собственных generic-параметров и без `Self` вне receiver; все связанные типы фиксируются.
  Иначе — `R-DIAG-TRAIT-001`. Значение, `sizeof`, разыменование, поле, сравнение адресов,
  зависимый от generic-параметров контракт, контракт без trait или с callable —
  `R-DIAG-TYPE-001`. Async-методы через заимствованный интерфейс — только `@scoped async`
  внутри task group (заимствования в async-кадрах по-прежнему запрещены, R-BORROW-0024).
- **L5.2.** Члены интерфейса — закрытые типы, которые программа к нему приводит, включая
  инстансы generic-функций; набор известен при сборке. Значение — адрес и тег (члены
  упорядочены по каноническим именам, так что C не зависит от порядка файлов); вызов —
  `switch` по тегу с прямыми вызовами реализаций. Heap-аллокации нет.
- **L5.3.** Сигнатура, checked errors, borrow-контракт и ресурсные атрибуты вызова — атрибуты
  прототипа trait, которым удовлетворяет каждая реализация; приведение проверяет traits,
  capabilities (`send`, `sync`) и равенства связанных типов типа-источника.
- **L5.4.** Граф стека и доказательства `@noalloc`/`@nonblocking` идут от вызова к реализации
  каждого члена: рекурсия через интерфейс — `R-DIAG-STACK-001`, аллоцирующий член —
  `R-DIAG-RESOURCE-001`. Проверка стека по сгенерированному C видит прямые вызовы.
- **L5.5.** Пример [keystore](../examples/keystore/README.md): бэкенд `slots` или `log`
  выбирается первым аргументом, все команды идут через одну не-generic функцию с
  `dyn(Store)*`; trait, реализации и использование — в разных модулях. Тесты:
  `codegen_dyn_interfaces`, `codegen_async_dyn_interfaces` (вызов каждой реализации, scoped
  async), случаи `dyn-*` в `semantic_tests.c` (несовместимый контракт, исключительный доступ,
  выход за время жизни, рекурсия, `@noalloc`), синтаксис в `frontend_tests.c`, интерфейс и
  независимость от порядка в `check_trait_contracts.py`, проба `dyn_interface` в аудите.

Вне этапа: загрузка сторонних реализаций, владеющие значения интерфейсов, преобразование
между интерфейсами, `->` через nullable-заимствование (общее ограничение языка) и интерфейсы
как generic-аргументы.

## Реализация от 24 сентября: L4.3 и L4.4, типизированные и связанные константы

Core — draft.58 (478 правил), interface schema 18.

L4.4. Константный параметр имеет любой целочисленный тип R или `bool`: `@generic<const bool
PACKED, const u32 MASK>` (R-TYPE-0047). Аргумент — константное выражение ровно этого типа,
неявных преобразований нет (`B<4u32>` для `usize` отклоняется), литерал без суффикса получает тип
параметра. Идентичность инстанса — тип и значение каждой константы; интерфейс записывает
`constant_type=u32` и `(constant u32 15)`.

L4.3. Trait объявляет связанные константы `const usize SIZE;` и `const bool PACKED = false;`
(новое правило R-TYPE-0050). Реализация связывает каждую константу без значения по умолчанию
записью `const usize SIZE = sizeof(Self);` и может переопределить значение по умолчанию;
значение — константное выражение объявленного типа, в том числе вызов, вычисляемый при
трансляции. `Self::NAME` доступно в значениях по умолчанию и телах методов, `T::NAME` — через
ограничение generic-параметра (включая supertraits), `Point::SIZE` и `Buffer<4usize>::SIZE` —
для закрытых типов. Над параметром константа зависима: граница `u8[T::SIZE]`, аргумент
`Buffer<T::SIZE>`, условие `@if (T::PACKED == true)` вычисляются для каждого инстанса. Закрытые
значения, нужные объявлениям уровня модуля до проверки реализаций (поле `u8[Point::SIZE]`,
`Frame<Point>`), считает разведочный проход. Каждая закрытая реализация вычисляет свои
константы, даже неиспользуемые. Диагностики: отсутствующее, лишнее или переопределённое с
другим типом связывание — `R-DIAG-TRAIT-001`, повтор — `R-DIAG-NAME-002`, неизвестное или
неоднозначное имя — `R-DIAG-NAME-001`, значение другого типа — `R-DIAG-TYPE-001`, цикл между
значениями — `R-DIAG-CONST-002`. Interface schema 18 добавляет в запись trait
`constants=((name="SIZE" type=usize default=false) …)`.

Тесты — `codegen_typed_constants`, `codegen_associated_constants` и их async-варианты, случаи
`typed-*` и `assoc-*` в `semantic_tests.c`, синтаксис в `frontend_tests.c`, интерфейс в
`check_const_generics.py`, проба `associated_constant` в аудите компилятора; примеры —
[tables](../examples/tables/README.md) (`trait Message`) и
[tournament](../examples/tournament/README.md) (`Draw::CAPACITY`).

## Реализация от 24 сентября: константные условия `@if`

Core — draft.55, дополнено в draft.56 и draft.57 (477 правил). Кроме `T is ...`, `core::profile is ...` и `core::target is ...`
в `@if` допускается константное условие — один лист условия R-STMT-0002: `true`, `false`,
явное сравнение или проверка принадлежности с константными операндами, включая вызовы,
вычисляемые при трансляции (R-META-0002). Атом считается предикатом типа, только если за типом
стоит `is`; как и в обычном `if`, одиночное значение без сравнения не допускается
(`@if (is_power_of_two(N) == true)`).

- В теле функции условие проверяется в области `@if` и вычисляется как обязательная
  константа: паника — `R-DIAG-CONST-003`, бюджет — `R-DIAG-LIMIT-001`, неконстантный операнд —
  `R-DIAG-CONST-002`. Неактивная ветвь не проверяется и не порождает кода.
- В generic-коде условие над `const usize N` или `sizeof(T)` остаётся зависимым: обе ветви
  проверяются в определении, каждая инстанциация вычисляет условие со своими аргументами
  (R-META-0003). Ошибка вычисления сообщается один раз с именем инстанса (`pick<0usize>`).
  Вызов generic-функции с зависимыми generic-аргументами (`size_of::<T>()`) тоже зависим: при
  инстанцировании он закрывается до конкретного инстанса, вычислимость проверяется для каждого
  `T` (draft.56, R-META-0003). Константа, которую читает только условие или граница массива,
  считается использованной (R-FUNC-0020).
- На уровне модуля условие выбирает объявления до их сбора, поэтому его значение вычисляет
  разведочный проход L4, который при таких условиях запускается до выбора объявлений. Условие
  может опираться на объявление, выбранное другим условием (следующий проход), но не на
  объявления собственных ветвей. Интерфейс записывает зависимость от исходников.

В draft.57 снято и второе ограничение: граница массива или константный аргумент
generic-объявления могут вызывать функцию над его параметрами (`u8[size_of::<T>()]`,
`Fixed<size_of::<T>() * 2usize>`). Формула проверяется в определении, вычисляется для каждого
закрытого инстанса; инстанс, закрытый на уровне модуля до тел функций (поле обычной структуры,
сигнатура), получает значение из разведочного прохода (R-TYPE-0047). Одинаковые формулы в одном
модуле — один тип, поэтому сигнатура и локальная переменная с `u8[size_of::<T>()]` совместимы.
Тесты — `codegen_computed_bounds`, `codegen_async_computed_bounds`, случаи `computed-*`,
`check_const_generics.py`.

Тесты — `codegen_static_values`, `codegen_async_static_values`, случаи `value-*` в
`semantic_tests.c`, синтаксис в `frontend_tests.c`, порядок модулей и профили в
`check_static_conditions.py`; пример — [tables](../examples/tables/README.md).

## Реализация от 23 сентября: L4, вычисление при трансляции (ядро)

Core — draft.54 (477 правил), Library — draft.21, interface schema 17. Обычная функция
вычисляется при трансляции без атрибута, когда её проверенное тело и вся цепочка вызовов
остаются в закрытом подмножестве (R-FUNC-0023): целые, `bool`, `char`, enum без payload,
строковые литералы, фиксированные массивы и структуры без drop из них, заимствования и срезы
своего хранилища, циклы, `switch`, `panic`, `core::wrapping_*`/`saturating_*`/`enum_name`/
`enum_ordinal` и вызовы таких же функций. Любая static или thread_local переменная, аллокация,
async, `unsafe`, FFI, checked errors или float оставляют функцию функцией времени выполнения.

Вызов с константными аргументами — translation-time call (R-EXPR-0032). Интерпретатор идёт
по проверенному HIR с проверками переполнения, деления, сдвигов, преобразований и границ как
в сгенерированном C и с раскладкой выбранной цели. Там, где константа обязательна (граница
массива, const-аргумент, значение enumerator, `case`, инициализатор модуля, `static`,
`thread_local`), паника — `R-DIAG-CONST-003`, превышение бюджета — `R-DIAG-LIMIT-001`,
невычислимая функция — `R-DIAG-CONST-002` с цепочкой причин. В обычном коде вызов заменяется
значением; паникующий или слишком дорогой вызов остаётся вызовом времени выполнения
(паника — наблюдаемый эффект; так работают, например, `fail_with("...")` в ветках ошибок).
Reflection-константы стали константными выражениями.

Типы уровня модуля (`struct Frame { u8[FRAME_BYTES] bytes; }`, значения enumerator)
проверяются до тел функций, поэтому при необходимости выполняется разведочный проход по тем
же исходникам во втором контексте; значения переносятся по узлу AST. Лимиты: 4 000 000 шагов
и 64 MiB значений на вычисление, не больше 8 разведочных проходов, до 256 скаляров при
подстановке в тело функции (константа модуля хранит любое значение как статический
инициализатор). Интерфейс отмечает вычислимые функции `consteval=true` и записывает
зависимости от исходников (L4.5, зависимость кеша). Пример — [tables](../examples/tables/README.md);
тесты — `codegen_consteval`, `codegen_async_consteval`, `semantic_consteval_*`,
`check_consteval.py`.

Запрет «прямого доступа к внешним переменным» реализован для вычислимости: функция, читающая
или меняющая static/thread_local состояние, в вычисление при трансляции не попадает. Общий
запрет для всех свободных функций язык не вводит: безопасный доступ к `thread_local` и
`unsafe`-доступ к изменяемым static остаются как прежде.

## 1. Решение и границы

Приоритет, заданный владельцем проекта:

> зафиксируй этот список работ и концентрируемся в первую очередь на расширении и доведении языка до полноты
> составь план и список работы в этом направлении

**Первый этап — расширение и завершение самого языка R.** Linux ARM64, инструменты
разработчика, отладка и полноценный прикладной сервис сохраняются в общей очереди; они
не определяют порядок ближайших языковых работ. Проверки корректности и регрессий
нужны при каждом расширении, а измерения сопоставимой производительности образуют
отдельный последующий результат.

Исходное предложение было рекомендацией, а не поручением: его совет начинать с Linux ARM64
заменён указанным выше приоритетом владельца.

Этот документ фиксирует очередь и порядок выполнения. Запрос от 19 сентября
разрешает реализацию L1, L2, L4, L5, L7, L8 и L9. Детали нового синтаксиса и спорные
семантические решения оформляются при проектировании соответствующего этапа.

## Реализация от 19 сентября: `out`, вариант A

Core — `0.1.0-draft.48`, interface schema — 16; Library остаётся draft.18.

- Реализованы `out T name` и `out place` для синхронных функций R и значений без
  borrowed payload. Частные выходы публикуются после успешного завершения `finally`;
  checked error сохраняет назначения вызывающего и очищает новые значения.

- L7 ещё не завершён: учёт каждой версии обычного возвращаемого результата и единое
  правило значимости обычных locals остаются следующим пакетом. Чтение/передача выхода
  подтверждает использование; перенос обязательства через произвольные копии не введён.

Проверки и точные границы: [отчёт по `out`](out-a-validation-2026-09-19.ru.md).

## 2. Что означает «полнота языка»

Уточнение от 20 сентября: безусловная замена локального значения простым `=`
запрещается даже после чтения старого значения; для нового результата требуется
новая переменная. [Решение и границы L7](local-results-design.ru.md).
Остальная очередь L8 → L4 → L5 → L9 → L6 подтверждена к реализации.

Цель — согласованный системный язык, на котором обычные обобщённые алгоритмы,
адаптеры, обработка ошибок и выбор реализации выражаются средствами R с понятными
контрактами. Приёмка состоит из двух самостоятельных результатов:

1. **Выразительность:** согласованные расширения работают вместе в библиотечном
   коде, включая передачу callable, точные ошибки, составные выражения и вычисления
   при компиляции.
2. **Соответствие:** для принятого нормативного объёма нет необъяснённых разрывов
   между спецификацией, семантикой, HIR/MIR, C17 и поведением программы. Все
   оставленные ограничения имеют правило, диагностику, тест и явное обоснование.

Число возможностей само по себе не является критерием завершения.
Сохраняются собственные основы R: отсутствие GC, детерминированное уничтожение,
явный Move, проверяемые borrow-контракты и ошибки, ограничение стека, ресурсные
гарантии, воспроизводимое преобразование в ISO C17.

Полнота выбранного языкового этапа и conformance конкретного target/profile —
разные утверждения. Пройденные тесты сами по себе не разрешают менять
`conformance_claim`.

- [x] **L1.1** Определить тип и идентичность function item, хранение через `auto`,

- [x] **L1.3** Определить получение закрытого callable из generic-функции,
  associated function и метода. Автоматическое связывание receiver и first-class

**Готово, когда:** функцию `normalize` можно напрямую передать в обобщённый

### L10. Заимствования в контейнерах и результатах

Решение владельца 25 сентября 2026: после L6 закрывать границы реализации H1 и H2. Правила

- [x] **L10.1** Параметр `const str[]` у обычных функций, методов, generic-инстансов и

- [x] **L11.1** Цели записи через представление: запись через займ или срез-локал достигает

### L15. Контракты регионов (G2)

- [x] **L15.1** Результат из содержимого параметра. Контракт различает хранилище, которое
  обозначает параметр, и то, что держит это хранилище или значение (символ содержимого
  L12). Вызов связывает такую часть результата с тем, что держит аргумент, а не с
  аргументом целиком; исключительные view, прочитанные из содержимого, остаются в регионе
  хранилища (R-BORROW-0021). Правило R-TYPE-0045 для связанных типов становится частным
  случаем. Примеры: декодер `take(Decoder* this, n)` с одновременно живыми `head` и `rest`,
  generic-помощник с `I*`.
- [x] **L15.2** Запись между параметрами. Функция, сохраняющая view одного параметра в
  хранилище, обозначенное другим (`split_into(str text, array<str>* parts)`,
  `feed(Parser* this, str chunk)`, generic `push(Stack<T>* this, T v)`), получает в
  контракте запись «содержимое j получает источники i». Вызывающая сторона добавляет
  источники аргумента i к тому, что держит хранилище аргумента j, в том числе транзитивно
  через собственные параметры. Заимствование хранилища параметра в него же (S8),
  автоматической памяти и неизвестного хранилища по-прежнему отвергается.
- [x] **L15.3** Владельцы с view. `own T*`, `rc T`, `arc T` и слабые владельцы, чья
  нагрузка держит view (`struct Node { own Node*? next; str word; }`), несут регион
  нагрузки (R-BORROW-0018, R-TYPE-0025). Разыменование владельца — проекция его хранилища.
  У разделяемых владельцев регион фиксируется при создании; `arc` с view передаётся только
  scoped-потокам. `core::adopt` и `from_raw` по-прежнему требуют нагрузки без регионов.

  сравнением (R-GRAM-0005);
- ветвь `switch` завершается неявным `break`, продолжение — только явным `fallthrough;`;
  выбор со значением остаётся выражением `match`, в ветви которого допускается `throw`;
  метки могут быть строками (точное сравнение) и значениями сопоставителя — core-трейта с
  проверкой одинаковых меток при сборке (`std.text::ignore_ascii_case`), в `switch` и `match`;
- вычисление при трансляции расширяется на checked-ошибки, float и контейнеры.

### L19. Цепочки вызовов с явным разрешением

- [x] **L19.1** Атрибут `@chain` у синхронного метода с результатом (собственного, прототипа
  трейта, члена реализации): после вызова такого метода выражение продолжается постфиксными
  суффиксами — следующим вызовом метода, полем, индексом. Продолжение после метода без
  `@chain` отвергается с подсказкой; форма со скобками `(a.f()).g()` остаётся. Каждый шаг
  подчиняется обычным правилам получателя: потребляющий `this` забирает временное значение,
  заимствовать временное по-прежнему нельзя (R-BORROW-0020), результат-займ продолжается
  через `->`.
- [x] **L19.2** Трейты, generic-код и dyn-интерфейсы: разрешение прототипа действует при
  вызове через ограничение и через dyn; член реализации следует прототипу.
- [x] **L19.3** Интерфейс, async (цепочка в async-теле, `await` последнего вызова), ошибка в
  середине цепочки (каждое промежуточное значение уничтожается ровно один раз), пример
  Builder-класса.

Выполнено 27 сентября (Core draft.71, interface schema 24): правило R-FUNC-0024; builder с
потребляющими звеньями, цепочка через займ и `->`, поле, индекс и элемент кортежа после звена,
цепочки через ограничение трейта и dyn-интерфейс, в async-функциях и после `await` проходят до
C17; брошенная посреди цепочки ошибка уничтожает builder ровно один раз; пример — заказ забора в
`examples/methods`. Найдены и исправлены дефекты L19-1 и L19-2; дефекты и итоговые проверки — в
разделе 16 матрицы.

**Готово, когда:** `Options::create().with_port(9000u16).with_capacity(128usize)` и
цепочка через займ проходят до C17 в синхронных и async-функциях, продолжение после метода
без `@chain` отвергается.

### L20. Выбор: `switch` и `match`

- [x] **L20.1** Неявный `break`: нормальное завершение ветви `switch` (и `select`) выходит из
  оператора; `fallthrough;` остаётся явным, `break;` — допустимым (R-STMT-0007).
- [x] **L20.2** `throw` как ветвь `match` типа `never`:
  `case variant o::none: throw Usage { .message = "unknown operation" };`.
- [x] **L20.3** Строковые метки с точным сравнением в `switch` и `match`; уникальность меток.
- [x] **L20.4** Сопоставитель меток — core-трейт: проверка метки значением сопоставителя,
  одинаковые метки находятся при сборке и отвергаются, поэтому порядок ветвей не важен;
  `default` обязателен; `std.text::ignore_ascii_case`.
- [x] **L20.5** Интерфейс, async, пример: выбор типа в `examples/calculator` одним `match`.

Выполнено 27 сентября (Core draft.72, Library draft.24): ветви `switch` и `select` без
терминатора завершаются неявным `break`; ветвь `match` может быть оператором `throw`; строки
сравниваются в `switch` и `match` побайтно; четвёртый core-трейт `core::CaseMatcher` (связанный
тип `Label`, метод `matches`) проверяет метки своих реализаций, а `std.text::ignore_ascii_case`
даёт сопоставитель без учёта регистра ASCII. Одинаковые метки отвергаются при сборке, если их
значения равны; `same` из исходного предложения не введён, потому что член трейта обязан иметь
получателя (R-TYPE-0041), поэтому среди эквивалентных для сопоставителя меток выигрывает первая по
порядку. `examples/calculator` выбирает операцию и тип числа двумя `match`. Итоговые проверки —
в разделе 17 матрицы.

**Готово, когда:** фрагменты владельца из `examples/calculator` (разбор операции и выбор типа)
пишутся через `match` без вспомогательных функций и цепочек `if`, ветви `switch` без `break`
проходят до C17, дубликаты меток сопоставителя отвергаются при сборке.

### L21. Наследование ошибок (A4)

- [x] **L21.1** Объявление `error net_error : io_error { u16 port; };`: одиночное
  наследование, наследник получает поля базы (раскладка — префикс), конструктор перечисляет
  поля плоско; циклы и база, не объявленная через `error`, запрещены.
- [x] **L21.2** Подтипы в эффектах: `throws io_error` покрывает поддерево; `catch (io_error e)`
  ловит поддерево, среди подходящих catch выигрывает ближайший предок независимо от порядка;
  значение базового типа хранит конкретный тип, `throw;` и `throw move e` его сохраняют;
  разбор — точными catch после rethrow, в том числе в другой функции.
- [x] **L21.3** Представление: семейство закрыто на сборке программы, как члены
  dyn-интерфейса; значение базового типа — тег и хранилище наибольшего члена без кучи;
  очистка, Copy/Move, Send/Sync — по членам; поля базы доступны через базовый тип.
- [x] **L21.4** Взаимодействия: наборы ошибок generic-функций, callable-эффекты, задачи,
  `select`, неявная граница `main`, интерфейс.
- [x] **L21.5** Общий корень стандартных ошибок; `main` ловит одну ошибку вместо семи.

**Готово, когда:** «поймать базу и разобрать в другой функции через rethrow» проходит до C17,
инфраструктурные ошибки ловятся одним catch, точные наборы и их проверки не ослаблены.

Выполнено 27 сентября (Core draft.73, Library draft.25, interface schema 25): правило R-AGG-0011
вводит родителя ошибки после `:`; значение типа ошибки с потомками — синтезированное семейство
(тег и хранилище наибольшего члена, закрытое при сборке программы), запись `throws` раскрывается
в точные ошибки поддерева, `catch` выбирает ближайшего предка в самом внутреннем подходящем
`try` (семантика, экземпляры generic, MIR и C17), `throw` значения базы бросает хранимую точную
ошибку. Корень стандартных ошибок — `std.error::fault` с `std.error::from_fault`
(R-SLIB-ERR-0004). Проверки: `codegen_(async_)error_families`, `codegen_error_family_modules`,
`codegen_(async_)standard_fault`, регрессии L21, пример `examples/settings`; подробности — в
разделе 18 [матрицы](language-completeness-matrix.ru.md).

### L22. Вычисление при трансляции: ошибки, float, контейнеры

- [x] **L22.1** Checked-ошибки: вычислимая функция может объявлять `throws` и содержать `try`,
  `catch`, `finally` и `throw`. Ошибка, брошенная при вычислении в месте, где константа
  обязательна, — ошибка трансляции с содержимым ошибки; в обычном коде такой вызов остаётся
  вызовом времени выполнения, а проверка эффектов вызывающего не меняется.
- [x] **L22.2** float: `f32`, `f64` и C-типы с плавающей точкой по правилам цели бит в бит
  (R-TYPE-0006, R-CMAP-0028); точные операции (`sqrt`, округления) вычисляются, трансцендентные
  — только при корректно округлённой реализации в компиляторе и runtime; `c_long_double` —
  программной эмуляцией, где цель требует binary128.
- [x] **L22.3** Контейнеры: аллокация и операции `array`, `list`, `dict`, `string` при
  вычислении; результат-контейнер в константе — замороженный объект образа программы (только
  чтение, освобождение не выполняется), раскладка и хеширование как в runtime.
- [x] **L22.4** Интерфейс и зависимости кеша, пределы вычисления, пример.

**Готово, когда:** `const u16 DEFAULT_PORT = parse_port("8080");`, таблица `f32` и константный
словарь вычисляются при сборке, а ошибка в константе останавливает сборку с понятной
диагностикой.

Выполнено 27 сентября (Core draft.74, Library draft.25 без изменений, interface schema 25):
R-FUNC-0023 допускает в вычислимых функциях checked-ошибки константных типов и стандартные
ошибки операций владельцев, `try`/`catch`/`finally`, значения binary32/binary64 с точными
`std.math` и корректно округлёнными `sqrt` и `remainder`, значения с тегом (`o<T>`, перечисления,
семейства ошибок) и владельцев `array`, `list`, `dict`, `std.string::string`; R-EXPR-0032
сообщает ошибку, покинувшую обязательную константу, через `R-DIAG-CONST-003` с её содержимым и
разрешает `const`-объектам хранить владельцев, замороженных в образе программы. Отличия от плана:
трансцендентные функции остаются вычислениями времени выполнения (корректно округлённой
реализации в runtime нет), эмуляции binary128 нет (цель использует binary64), ёмкость не
наблюдается. Проверки: `codegen_(async_)consteval_checked`, `codegen_(async_)consteval_floats`,
`codegen_consteval_owners`, `codegen_(async_)consteval_frozen`, регрессии L22, пример
`examples/settings`; подробности — в разделе 19 [матрицы](language-completeness-matrix.ru.md).

### L23. Структурные дедлайны (A2)

- [x] **L23.1** Дедлайн блока или группы задач задаётся один раз и наследуется всем, что
  запущено внутри, как отмена; стандартная операция без явного дедлайна использует
  ближайший, явный дедлайн его сужает.
- [x] **L23.2** Истечение даёт операции `timed_out`, а не `cancelled`; потомки видят тот же
  дедлайн; согласование с `first_until`, `all_until` и `select`.
- [x] **L23.3** Библиотека и runtime Darwin: дедлайн задачи хранится в кадре и применяется при
  native-подаче.

**Готово, когда:** дедлайн в `netlab` не передаётся ни разу (§21.3 плана фундамента), а истечение
ведёт себя как прежде.

Выполнено 27 сентября (Core draft.75, Library draft.26, interface schema 25): правило
R-STMT-0019 вводит контекстный оператор `deadline (value) { ... }` в async-функциях: пока блок
выполняется, дедлайн задачи — более ранний из прежнего и значения, любой выход из блока его
восстанавливает, а задача, запущенная внутри (async-вызов, участник группы, стандартная
операция), получает его при запуске. R-SLIB-ASYNC-0008 разрешает опускать последний аргумент
`deadline` у всех 61 операции и берёт более ранний из аргумента и дедлайна задачи;
`first_until`, `all_until` и `select` с `until` заканчиваются не позже дедлайна задачи. Дедлайн
группы записывается блоком, содержащим группу или находящимся в её теле; вычисление и ожидание
задач он не прерывает. Проверки: `codegen_deadline_blocks`, регрессии L23, модульный тест
runtime, пример `examples/netlab` (17 передач дедлайна → 0); подробности — в разделе 20
[матрицы](language-completeness-matrix.ru.md).

### L24. Сервисный код (A3, A5, B4)

- [x] **L24.1** Асинхронные каналы: получение — асинхронная операция, которую можно запустить
  участником группы; существующий `select` покрывает «канал, таймер или отмена».
- [x] **L24.2** `std.service::serve`: цикл `accept`, обработчик на соединение в группе до
  `capacity`, политика переполнения, таймаут соединения, ошибки обработчиков в отчёте, мягкая
  остановка по отмене.
- [x] **L24.3** `examples/service` и переписанный `netlab`: вызов I/O — одна строка, дедлайн —
  ноль передач, `catch` в `main` — один, `deliver` — не больше половины прежнего объёма;
  гарантии владения, отмены и дедлайнов прежние.

**Готово, когда:** метрики раздела 21.3 плана фундамента выполнены на `examples/service` и `netlab`,
а тесты владения, отмены и дедлайнов зелёные.

Выполнено 27 сентября (Core draft.76, Library draft.27, interface schema 25):
`std.sync::receive` и метод `receiver.receive()` (R-LIB-0016) принимают из канала асинхронно:
приём — задача, которую можно запустить участником группы или ветвью `select`; отмена не теряет
значение, а `o::none` означает, что отправителей не осталось. R-STMT-0017 разрешает отсоединять
участника группы (`std.async::detach`), не снимая его с контроля группы. R-модуль `std.service`
(R-SLIB-SERVICE-0001..0003) даёт `serve` и `serve_with`: цикл accept, обработчик на соединение в
группе до `capacity` (не больше 1024), отказ при переполнении, таймаут соединения блоком
`deadline`, отчёт с ошибками обработчиков, остановку каналом (`drain` или `cancel`) и отменой
задачи. `examples/service` показывает эхо и счётчик с общим состоянием; в `netlab` вызов I/O
занимает одну строку, дедлайн не передаётся, `main` ловит один `std.error::fault`, а `deliver`
сократился с 37 до 18 строк при тех же проверках. Найдены и исправлены дефекты L24-1 (строковые
метки по `constexpr str` в async-функции) и L24-2 (чтение освобождённой памяти при понижении
`receive`, найдено ASan). Ожидание вызова, бросающего весь корень `std.error::fault`, раскрывается
по 24 членам корня, поэтому корень пишется на границах, а внутренние функции объявляют точные
наборы ошибок (ограничение снято на L25). Подробности — в разделе 21
[матрицы](language-completeness-matrix.ru.md).

### L25. Вариадические view, ёмкость и ожидание слота групп, общий выход ошибок

- [x] **L25.1** Хвост аргументов одним срезом: вариадический параметр разделяемых view
  (`str... words`) и передача среза `calculate(...arguments[1..])`.
- [x] **L25.2** Ёмкость `task_scope` через константу generic, проверяемая для каждого инстанса.
- [x] **L25.3** Барьер группы «есть свободный слот» (`await group.vacancy()`,
  `group.vacancy_until(deadline)`) и политика `overflow::wait` в `std.service`.
- [x] **L25.4** Оптимизация компилятора: ошибки вызова, идущие в вызывающую функцию или в один
  `catch` семейства, передаются целиком одним путём вместо пути на каждый вид.

**Готово, когда:** `examples/calculator` передаёт аргументы срезом; `std.error::fault` в любой
функции не увеличивает код и стек заметно больше точного набора, а `std.service` с корнем во
всех функциях проходит под ASan; сервис с политикой ожидания не отклоняет соединения сверх
ёмкости.

Выполнено 28 сентября (Core draft.77, Library draft.28, interface schema 25): элемент
вариадического параметра может быть разделяемым view, срез передаётся как `...arguments[1..]`
(R-FUNC-0018), и `calculate` в `examples/calculator` принимает `str... words` вместо семи
параметров. Ёмкость группы может зависеть от констант generic (R-STMT-0017): она вычисляется
при закрытии инстанса, а недопустимое значение сообщается с именем инстанса. Ожидания
`vacancy` и `vacancy_until` (R-STMT-0018) ждут свободного слота группы; на них `std.service`
реализует `overflow::wait` (R-SLIB-SERVICE-0001, R-SLIB-SERVICE-0003), `examples/service`
использует эту политику. Члены носителя ошибок с одинаковой очисткой выходят одним путём
через функцию-реле (R-ERR-0001): проба с тремя `await` вызовов, бросающих `std.error::fault`,
уменьшилась с 4892 до 2483 строк C, а `std.service` с корнем во всех функциях под ASan вместо
`stack_exhaustion` проходит все сценарии. Помощники `examples/service` снова объявляют
`throws std.error::fault`. Подробности — в разделе 22 [матрицы](language-completeness-matrix.ru.md).

### Анализ пробелов и решение владельца от 28 сентября 2026

После L25 проведён анализ того, чего не хватает языку и стандартной библиотеке для базовых
прикладных программ. Платформенные работы в анализ не входили: Linux-порт, владельцы
FD/shared memory, LSP, форматтер, отладчик и зависимости остаются в
разделе 7. Проверены Core draft.77 (485 правил), Library draft.28 (240 правил, 40 модулей),
грамматика Annex A, дорожная карта L0–L25, матрица и примеры `service` и `netlab`.

Вывод анализа: по владению, ошибкам, async и generics ядро для сервисов достаточно.
Пробелы остались там, где программе нужно единообразно хранить реализации, выводить типовые
реализации для структур и работать с блокирующим миром. В библиотеке нет протоколов
прикладного уровня, TLS, сигналов, логирования, случайных чисел и тестовой инфраструктуры.

Библиотека разбита на три уровня: фундамент (M18–M24), протоколы (M25–M27) и прикладные модули
(M28–M31). Нумерация M продолжает вехи [плана фундамента](foundation-plan.ru.md): M16 —
`std.deflate`, M17 — `std.xml`. Внешние C-библиотеки подключаются через проверяемый FFI
(R-FFI-0028..0044): mbedTLS 3 для TLS, libsodium для криптографии; SQLite с M33 собирается из
amalgamation, которую скачивает CMake (в M29 была системная libsqlite3).

Решение владельца (28 сентября 2026): реализовать весь перечень — двенадцать языковых пунктов и
три уровня библиотеки; платформенные работы остаются вне этапа. Порядок выполнения задаёт
таблица раздела 4: языковые пункты, от которых зависят модули, идут раньше этих модулей. Каждый
этап выполняется по правилу раздела 8: норма EN и RU, путь parser → semantic → HIR/MIR → C17,
позитивные и негативные проверки, пример, инвентари и запись приёмки в матрице. Новый публичный
API и новый узел синтаксиса получают маршрут в приложениях каталога примеров.

### L28. Указатели на функции

- [x] **L28.1** Тип `fn [@noalloc] [@nonblocking] (P...) -> R [throws(E...)]` и
  `async fn (P...) -> R [throws(E...)]` как значение: Copy, Send+Sync, ненулевой; отсутствие —
  `o<fn(...) -> R>`; поля, элементы контейнеров, параметры, результаты и generic-аргументы.
- [x] **L28.2** Function item (R-FUNC-0007), в том числе закрытый generic и метод, неявно
  преобразуется при точном совпадении параметров, результата, набора ошибок и формы
  sync/async; ресурсные гарантии можно забыть, нельзя усилить; результат может заимствовать
  только то, что разрешает контракт типа.
- [x] **L28.3** Множество целей типа — все функции, преобразованные к нему в программе, как
  члены dyn-интерфейса: граф вызовов (R-FUNC-0004), стек и ресурсные доказательства проходят
  по каждой цели; цикл через указатель — `R-DIAG-STACK-001`.
- [x] **L28.4** Представление — номер целевой функции и выбор по целям типа с прямым вызовом
  каждой (для async — запуск кадра выбранной функции с двухфазной транзакцией), как у
  dyn-интерфейсов; сравнение `==` и `!=` значений одного типа. Указатель на функцию C17 не
  выбран: async-запуск всё равно требует выбора кадра по цели, а прямые вызовы сохраняют точный
  граф вызовов для инструмента стека.

**Готово, когда:** таблица команд `dict<str, fn(...) -> ...>` в примере заменяет цепочку
сравнений, async-обработчики хранятся в структуре; фикстуры покрывают checked-ошибки, отказ
запуска, рекурсию через указатель и ресурсные контракты.

Выполнено 28 сентября (Core draft.80, 488 правил; Library draft.30; interface schema 28): новое
правило R-TYPE-0054 вводит типы функций. Function item, в том числе закрытая generic-функция и
метод, преобразуется к типу функции при точном совпадении сигнатуры, checked errors и формы;
значение с большим набором гарантий преобразуется к типу с меньшим. Значение вызывается через
локальный объект, поле, элемент, результат вызова и `(expression)(args)`, в том числе из другого
модуля; async-значение запускается как прямой вызов, отказ запуска оставляет его пригодным.
Значение удовлетворяет callable-ограничению своей сигнатуры, а generic-вывод берёт параметры из
сигнатуры function item. Цели типа собираются из программы после закрытия всех инстансов;
рекурсия через значение сообщается у замыкающего преобразования, а вызов через значение
доказывает `@noalloc` и `@nonblocking` ровно гарантиями своего типа. Пример `examples/dispatch`
выбирает списочные команды из `dict<str, fn(const i32[], str) -> ...>` вместо перечисления и

Подробности и итоговые проверки — в разделе 25 [матрицы](language-completeness-matrix.ru.md).

слабые формы. Владелец типа, доказывающего контракт и не держащего view, преобразуется в того же

называемого типа. Пример `examples/keystore` хранит выбранное хранилище как `own dyn(Store)*` в
структуре `Session`. На этапе исправлены три существовавших дефекта: `switch` по временному
`o<...>` не уничтожал его, класс клея владельцев мог получить представителя без уничтожения, а
рантайм процессов терял событие завершения дочернего процесса. Подробности и итоговые проверки —
в разделе 26 [матрицы](language-completeness-matrix.ru.md).

### L30. Асинхронная синхронизация и обратное давление

- [x] **L30.1** `std.async::mutex<T>` и `std.async::rw_lock<T>`: Move-only Send+Sync handles с
  явным `clone`; `await m.lock()` даёт владеющий Send-guard, доступ через `guard.get()` и
  `guard.get_mut()` между приостановками; порядок FIFO; отмена ожидания ничего не теряет.
- [x] **L30.2** `std.async::semaphore` с владеющими разрешениями и `std.async::notify`
  (`notify_one`, `notify_all`, `await n.notified()`).
- [x] **L30.3** Ограниченный канал: `await sender.reserve()` даёт `std.sync::permit<T>`, отправка
  через разрешение не ждёт и не отказывает; `try_reserve`; `std.async::broadcast<T: clone>` с
  результатом `lagged(n)` для отставшего подписчика.
- [x] **L30.4** Core: не-Send значение (guard `std.sync`) не живёт через `await` — диагностика
  называет замену из `std.async`.

**Готово, когда:** обработчик `count` в `examples/service` хранит состояние под
`std.async::mutex`, медленный подписчик ограниченного канала держит память в пределах
ёмкости (фикстура на 10^5 сообщений), тесты отмены и порядка зелёные под TSan.

Выполнено 28 сентября (Core draft.82, 489 правил; Library draft.31, 244 правила; interface
schema 28 без изменений): правила R-SLIB-ASYNC-0013..0016 вводят `std.async::mutex<T>`,
`rw_lock<T>`, `semaphore`, `notify` и `broadcast<T>`, а R-LIB-0016 — резерв слота
ограниченного канала `reserve`/`try_reserve` с разрешением `std.sync::permit<T>`. Дескрипторы
Move-only, `clone` явный; guard и разрешение держат ссылку на свою блокировку и поэтому живут
через `await`. Ожидающие обслуживаются в порядке запуска, освободившийся ресурс передаётся
первому из них, `try_*` отказывает, пока очередь не пуста, а отменённое ожидание ничего не
забирает: выбор исхода предшествует передаче. `broadcast` клонирует значение для каждого
подписчика; переполненная очередь подписчика теряет старейшие значения и сообщает `lagged(n)`
перед следующим, `closed` приходит после очереди, когда не осталось дескрипторов. Нулевая
ёмкость `broadcast` и резерв в канале без буфера — нарушение контракта. Core R-FUNC-0011: guard
`std.sync` или несущий его исход блокировки через `await` отвергается диагностикой, которая
называет `std.async::mutex` или `std.async::rw_lock` (L30.4); Annex A получил вызов
`std.async::broadcast::<T>(capacity)`. В `examples/service` обработчик `count` держит итог под
`std.async::mutex` и сообщает аудитору через канал на два значения (`try_reserve`, затем
`reserve`), а новый режим `watch` показывает `rw_lock`, `semaphore`, `notify` и `broadcast` с
детерминированным `lagged`. Фикстура `codegen_async_broadcast` проводит 10^5 значений через
очередь на 64 к быстрому и медленному подписчику; фикстуры блокировок, резерва и отмены зелёные
под ASan и TSan. На этапе исправлены два существовавших дефекта: ожидаемый тип всего
постфиксного выражения доставался его голове, а адрес результата вызова под `->` в
async-функции не понижался. Подробности и итоговые проверки — в разделе 27
[матрицы](language-completeness-matrix.ru.md).

### L31. Блокирующие вызовы

- [x] **L31.1** `std.async::blocking(entry, arguments...) -> task<R throws E...>`: первый операнд —
  прямой designator безопасной функции, как у `std.thread::spawn`; аргументы Send и unborrowed
  проходят двухфазную транзакцию; вызов исполняется на отдельном пуле потоков runtime,
  завершение приходит как native completion.
- [x] **L31.2** Отмена удаляет ещё не начатую работу; начатый вызов не прерывается, исход
  `cancelled` публикуется после его возврата (как у полосы файловой системы); размер пула
  записан в манифесте цели.

**Готово, когда:** пример вызывает блокирующую C-функцию, а другие задачи продолжают
выполняться; фикстуры проверяют отмену до и после начала, ошибки запуска и исчерпание пула.

Выполнено 28 сентября (Core draft.83, 490 правил; Library draft.32, 245 правил; interface
schema 28 без изменений): новое правило R-SLIB-ASYNC-0017 вводит
`std.async::blocking(entry, arguments...) -> task<R throws E...>`, а Core R-TERM-0015 — пул
блокирующих вызовов: не больше четырёх потоков, отдельных от исполнителя и от полосы файловой
системы, которые исполняют только точки входа `std.async::blocking`. Точка входа и аргументы
проверяются как у unscoped `std.thread::spawn`, результат и проверяемые ошибки точки входа
становятся исходом задачи, старт бросает `std.async::start_error` и при неудаче оставляет
staged-аргументы у вызывающего. Вызовы берутся в порядке отправки; отмена снимает вызов, который
ещё не взят потоком, вместе с аргументами, а взятый вызов не прерывается: задача подтверждается
после его возврата, и его результат уничтожается. Потоки пула создаются по требованию, число
потоков и предел очереди записаны в манифесте цели (`blocking_call_pool`) и сверяются с
константами рантайма; R-CONF-G005, R-CONF-G012, R-SLIB-PROFILE-0002/0003, R-SLIB-ASYNC-0010 и
R-SLIB-MAP-B005 признают пул вторым допустимым блокирующим адаптером. Пример `examples/offload`
вызывает libc `usleep` в шести вызовах на четырёх потоках, пока тикер продолжает работать, и
показывает отмену взятого вызова. На этапе исправлен существовавший дефект: аудит поверхности
библиотеки завершался ошибкой из-за неиспользованных результатов в своих пробах. Подробности и

schema 29): объявление поля может заканчиваться `= initializer` (R-INIT-0004), вариант enum —

значение типа поля в модуле агрегата, без локальных объектов инициализирующего кода — и

использования указывает на неё. Значение по умолчанию (R-INIT-0005) теперь бывает нулевым и

Выполнено 29 сентября (Core draft.86, 490 правил; Library draft.35, 254 правила; interface
schema 29): новый раздел 21.9 Library вводит R-source modules `std.stream`, `std.bufio` и
`std.console`. Трейты `Reader`, `Writer` и `Stream` со `@scoped`-методами и ошибкой
`std.error::fault` реализованы для `std.io::input` и `output`, файлов, TCP-потоков и принятых
соединений, для `std.stream::duplex<R, W>` (два pipes процесса или стандартные ввод и вывод как
один поток) и для владельцев интерфейсов `own dyn(...)*`, поэтому поток, выбранный во время
работы, служит источником буферизованного читателя. Читатель `std.bufio` выдаёт строки,
последовательности до разделителя, ровно N байт и куски, строка обязана помещаться в буфер;
писатель собирает записи и отдаёт их явным `flush`. `std.console` печатает одним `write_all` и
читает строку по байту, не заходя за line feed. Язык для этого изменён в двух местах:
реализация трейта для стандартного типа может повторять имя стандартного метода, а receiver form
по-прежнему называет стандартный метод (R-NAME-0010); интерфейс доказывает capabilities,
которые его трейты требуют от `Self`, и `dyn(Reader)` — тот же интерфейс, что
`dyn(Reader & send & sync)` (R-TYPE-0051). Стандартные структуры ошибок строятся
braced-инициализацией (R-SLIB-ERR-0003). Исправлены дефекты M18-1..M18-9: неиспользуемый move
gate в C, flush через заимствованный поток, `@scoped`-метод через `value.method()`,
непересекающиеся поля в аргументах вызова, await в условии цикла, повтор цикла для значений без
views, контекст среза в generic-вызове и владелец методов стандартной структуры. Все примеры
печатают через `std.console`, `examples/support/console.r` удалён, а пример `examples/relay`
читает строки stdin, записи файлов и ответы TCP и pipe через `std.bufio`. Подробности и
итоговые проверки — в разделе 31 [матрицы](language-completeness-matrix.ru.md).

### M19. Текст, байты, кодировки

- [x] **M19.1** `std.text`: `split`, `lines`, `trim`, `join`, `replace`, смена регистра ASCII,

- [x] **M19.2** `std.bytes`: курсоры чтения и записи `u16`/`u32`/`u64` в LE и BE с проверкой

- [x] **M19.3** `std.encoding`: base64 (стандартный и URL-алфавит), hex, percent-encoding.

**Готово, когда:** пример приложения использует каждую новую операцию; дифференциальные тесты
кодировок против Python.

Выполнено 29 сентября (Core draft.87, 490 правил; Library draft.36, 266 правил; interface
schema 30). `std.text` получил операции над views без аллокаций — `split`, `lines`, `trim`,
`trim_start`, `trim_end`, итерацию по скалярам, границы скаляров и `to_ascii_upper` — и с
profile `hosted`, где есть `std.string`, `join`, `replace`, `ascii_uppercase` и
`ascii_lowercase`. У C-модулей
`std.string` и `std.bytes` появились R-части, которые загружает `import`: `replace_range` и
`insert_str` проверяют границы скаляров до аллокации и при ошибке не меняют строку, а
`std.bytes::cursor` читает и пишет `u8`..`u64` в LE и BE и при нехватке байт сообщает
`out_of_bounds`, не сдвигая позицию. Новый R-source module `std.encoding` записывает base64 с
дополнением, base64url без него, hex и percent-encoding RFC 3986, а декодирование принимает
только канонический текст и сообщает `std.convert::parse_error` с индексом байта в
определённом порядке проверок. `std.iter` получил `filter`, `reversed`, `chunks`, `windows`,

предпочтительный, повторяемая группа сообщает последнюю итерацию. Для `min`, `max` и `sum` язык
получил ограничения ассоциированных типов в заголовке generic-функции,
`@generic<I: core::Iterator, I::Item: std.cmp::Ordered>` (R-TYPE-0043); они проверяются при
каждой инстанциации, в том числе с зависимыми аргументами. `std.convert::parse_error` строится
braced-инициализацией (R-SLIB-CONV-0001). Исправлены дефекты M19-1 (HIR-вывод безымянного
носителя ограничения) и M19-2: R-модули и R-части, объявленные в profiles ниже тех, что дают

`std.iter`, `std.heap`, `std.sorted`, `std.deflate`, `std.xml` в `allocation`, `std.text` в

profile отвергается на месте импорта, а проверка `check_library_profiles.py` транслирует
каждый module карты библиотеки во всех profiles. Пример `examples/textkit` использует каждую новую операцию и синтаксис
`I::Item:`, дифференциальный тест сравнивает `std.encoding` со стандартной библиотекой Python
на 2240 случаях, а тест отказов аллокации проходит все 45 точек. Подробности и итоговые
проверки — в разделе 32 [матрицы](language-completeness-matrix.ru.md).

### M21. Форматы времени

- [x] **M21.1** Запись и разбор RFC 3339, запись и разбор HTTP-date (IMF-fixdate).
- [x] **M21.2** `std.time::interval`: периодические тики без накопления сдвига.

**Готово, когда:** пример `clock` использует форматы, а тики интервала проверены под нагрузкой.

Выполнено 29 сентября (Core draft.87 без изменений, 490 правил; Library draft.38, 277 правил;
interface schema 30). У C-модуля `std.time` появилась R-часть, которую загружает
`import std.time;`: `format_rfc3339` пишет UTC-время RFC 3339 с 0–9 цифрами дробной части,

любой длины и смещение, а `parse_http_date` — все три формы HTTP-date, которые RFC 9110

(`below_minimum`/`above_maximum` в первой цифре поля; секунда 60 выше максимума).

неизменным. Исправлены дефекты M21-1 (выражения-конструкторы `Type {...}` не строили записи

`target_info` не принимал и типизированную инициализацию) и M21-2 (значения стандартного
enum, например параметр и поле `code` пойманной ошибки, не сравнивались, если в функции не
был назван ни один вариант этого enum). Пример `clock` пишет и читает даты и тикает
интервалом (55 проверок), тики проверены под нагрузкой двумя вычислительными задачами, а
дифференциальный тест сверяет 4720 случаев записи и разбора, включая коды и индексы ошибок
случайных правок текста, с эталоном по правилам и стандартной библиотекой Python. Подробности
и итоговые проверки — в разделе 34 [матрицы](language-completeness-matrix.ru.md).

### M22. Сигналы и расширенная сеть

- [x] **M22.1** `std.signal`: асинхронное ожидание SIGTERM, SIGINT, SIGHUP, SIGUSR1 и SIGUSR2
  участником группы и ветвью `select`.
- [x] **M22.2** Unix-сокеты: stream, datagram, listener, учётные данные собеседника.
- [x] **M22.3** Опции сокетов: nodelay, keepalive, TTL, размеры буферов, broadcast, multicast;
  подключение по имени с перебором адресов.

**Готово, когда:** `examples/service` останавливается по SIGTERM с drain, пример обменивается
данными через Unix-сокет.

Выполнено 29 сентября (Core draft.87 без изменений, 490 правил; Library draft.39, 287 правил;
interface schema 30). Новый C-модуль `std.signal` (profile `hosted-native-async`) доставляет
сигналы как завершения задач, и ни одна строка R не выполняется в обработчике: `listen(kind)`
создаёт listener, который считает доставки с момента создания, `await listener.next()`
завершается их числом (минимум одна) и может проиграть в `select`, оставив доставки следующему
ожиданию, а `raise(kind)` посылает сигнал самому процессу. Пока listener вида существует, сигнал
не выполняет ни действие по умолчанию, ни прежнюю диспозицию; последний listener её
восстанавливает, а дочерний процесс `std.process::spawn` начинает с диспозицией по умолчанию.
`std.net` получил R-часть с `tcp_connect_any` (кандидаты по порядку, ошибка последней
попытки) и `@scoped tcp_connect_name` (разрешение имени и тот же перебор), опции сокетов
(`tcp_options`/`udp_options` читаются и меняются целиком, сначала проверка всей записи, затем
только изменённые поля; keepalive округляется вверх до целых секунд) и multicast
(`udp_join_multicast`/`udp_leave_multicast`, ноль — интерфейс по маршрутам цели), а также
Unix-domain сокеты: `unix_listen`/`unix_accept`/`unix_connect`, scoped-чтение и запись,
`unix_shutdown`/`unix_close`, `unix_peer_credentials` (effective uid/gid и pid собеседника) и
датаграммы `unix_datagram_bind`/`unix_datagram_connect`/`unix_send_from`/`unix_receive_into`.
`std.net::unix_stream` реализует `std.stream::Reader`, `Writer` и `Stream`. Исправлены
дефекты M22-1 (receiver-форма операции стандартного enum через квалифицированную константу,
`std.signal::kind::user1.raise()`, давала внутреннюю ошибку), M22-2 (дочерний процесс
наследовал маску сигналов потока Dispatch, и SIGUSR2 его не завершал), M22-3 (представление

**Готово, когда:** модули библиотеки на R имеют тесты на R, запускаемые из CTest.

Выполнено 29 сентября (Core draft.88, 491 правило: новое R-FUNC-0025, изменены R-FUNC-0008 и
R-GRAM-0007; Library draft.41, 300 правил: новые R-SLIB-TEST-0001..0003, изменены

изменений). Атрибут `@test` отмечает тестовую функцию: функцию области module без параметров и

проходит, только если тест бросает ошибку, которую принимает catch `E`. `@test(allocations)`

каждом повторе отказывает именно эта попытка. Тестовый режим `r-front --test` добавляет в module
точки входа `async i32 main()`. Он выполняет тесты в порядке объявления и печатает
`test NAME ... ok` или `FAILED:` с сообщением утверждения, переносимым именем стандартной ошибки
или типом другой ошибки, затем итог; возвращает 0 или 1. Новый module `std.test`: C-часть
управляет счётом попыток hosted allocator (`allocation_attempts`, `fail_allocation_at`), R-часть
содержит утверждения `check`, `fail`, `equal`, `not_equal`, `equal_text`, `contains` и учёт
прогона `runner`. Каждый module библиотеки, написанный на R, и каждая R-часть C-module получили
тесты на R в `library/r/tests` (27 файлов, 215 тестов); CTest собирает их в тестовом режиме и
запускает (`r_frontend_codegen_rtest_*`). Тесты нашли и помогли исправить десять дефектов:
M24-1 — план линковки синхронной программы с табличными операциями `std.async`/`std.test` не
называл их библиотеку; M24-2 — `std.string::string` как ключ `dict` не компилировался, а
словари `std.env` хешировали строки иначе, чем сгенерированный код; M24-3 — `pop_front` и
`pop_back` `std.deque` при отказе выделения во время перекладывания теряли или переставляли
элементы; M24-4 — неудачная вставка в `std.sorted::map` оставляла ключ без значения; M24-5 —
перегрузка `append` отвергала результат вызова R-функции, метода и generic-функции; M24-6 —
после первой ошибки в теле появлялись ложные диагностики (повтор значения и неполнота `switch`
по enum, несогласованные аргументы generic-вызова); M24-7 — `std.xml` принимал ссылку на символ
вне XML 1.0 и `]]>` в тексте; M24-8 — `std.bufio::writer` буферизовал данные длиной ровно в
ёмкость буфера; M24-9 — `std.args` разрешал `remaining("help")`; M24-10 — форма
`std.module::type::method(receiver, ...)` метода стандартного типа (R-NAME-0010) отвергалась.
Пример `examples/testing` тестирует module версий. Подробности и итоговые проверки — в разделе
37 [матрицы](language-completeness-matrix.ru.md).

### M32. Model Context Protocol

Запрос владельца от 30 сентября 2026: протокол MCP нужен в
стандартной библиотеке. Этап следует за M27 (решение владельца: этапы идут по порядку); ему нужны
`std.json`, `std.http` с SSE и `std.process`. Целевая ревизия — 2026-07-28: протокол без состояния (версия, возможности и
идентичность клиента в `_meta` каждого запроса), обязательный `server/discover`, Streamable HTTP
без сессий и GET-потока, взаимодействие сервера с клиентом через Multi Round-Trip Requests,
`subscriptions/listen` для уведомлений об изменениях; sampling и logging объявлены устаревшими и
не реализуются.

- [x] **M32.1** `std.jsonrpc`: сообщения JSON-RPC 2.0 (запрос, уведомление, ответ, ошибка,
  id числом или строкой, коды -32700…-32603) над `std.json::value`; кадрирование
  «JSON в строке» поверх любого `std.stream::Stream` (связка stdio).
- [x] **M32.2** Сервер `std.mcp`: `_meta` каждого запроса, `server/discover` и
  `UnsupportedProtocolVersionError`; tools (`tools/list` с `inputSchema` и `outputSchema`,
  `tools/call` с content и `structuredContent`, `isError`), resources (`resources/list`,
  `resources/read`, шаблоны), prompts (`prompts/list`, `prompts/get`), курсоры страниц,
  `ttlMs` и `cacheScope`; progress и отмена; elicitation через `InputRequiredResult` и
  `inputResponses`; `subscriptions/listen` с `list_changed` и `resources/updated`.
- [x] **M32.3** Транспорты: stdio (сервер как дочерний процесс, клиент запускает его через
  `std.process`) и Streamable HTTP поверх `std.http`: один эндпоинт, POST, ответ JSON или
  SSE-поток запроса, заголовки `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` и
  `Mcp-Param-*` из `x-mcp-header` (Base64-sentinel) с проверкой совпадения с телом
  (`HeaderMismatch`, -32020), проверка `Origin` (403), 202 для уведомлений, 405 для GET и DELETE,
  отмена закрытием потока, комментарии keep-alive на потоках listen.
- [x] **M32.4** Клиент `std.mcp`: discover, list и call, цикл MRTR с обработчиком elicitation,
  потоки listen; поверх stdio и HTTP. Для этого `std.http` получает чтение тела ответа по частям
  на клиенте и отмену обработчика сервера при обрыве соединения.
- [x] **M32.5** Авторизация HTTP: bearer-токены OAuth 2.1 на стороне ресурсного сервера
  (Protected Resource Metadata RFC 9728, `WWW-Authenticate`); полный поток авторизации клиента
  (PKCE) — после M28, когда появится криптография.
- [x] **M32.6** `std.json::schema::<T>()`: JSON Schema (draft 2020-12) из типов R, построенная по
  той же модели, что `std.json::marshal`/`unmarshal` (имена и обязательность полей по `@json`,
  `o<T>` как null, массивы и словари, пределы целых типов, варианты enum, `$defs`/`$ref` для
  вложенных и рекурсивных типов); новый параметр `@json(description = "...")` (правило Core) и
  hook `T::json_schema()` для типов с собственными конвертерами; проверка схемы против
  `marshal`/`unmarshal` того же типа.

**Готово, когда:** пример-ассистент отдаёт tools, resources и prompts по stdio и по HTTP,
клиент `std.mcp` вызывает их, проходит elicitation и получает `list_changed`, а независимая
реализация (MCP Inspector или официальный SDK с поддержкой ревизии 2026-07-28) работает с

### L34. Бюджеты ресурсов

- [x] **L34.1** Оператор `budget (limits) { }` в async-функциях: лимиты байтов и задач
  наследуются запущенными задачами, как дедлайн (R-STMT-0019); вложенный бюджет сужает внешний.
- [x] **L34.2** Runtime учитывает каждое выделение в бюджете задачи и возвращает его при
  освобождении после выхода из блока; превышение — `alloc_error::budget_exhausted` и
  `start_error::budget_exhausted`.

**Готово, когда:** обработчик соединения в сервисе ограничен бюджетом, а отказ на границе
бюджета освобождает только построенные компоненты.

Выполнено 1 октября (Core draft.90, 492 правила: новое R-STMT-0020, грамматика —
`budget-statement` и вариант `budget_exhausted` в `standard-async-variant-name`, 297 продукций;
Library draft.47, 369 правил: новое R-SLIB-ALLOC-0003 — R-часть `std.alloc` с
`std.alloc::limits`, изменены R-LIB-0004, R-SLIB-ASYNC-0002, R-SLIB-GEN-0005, R-SLIB-RSRC-0002
и Annex A). `budget (std.alloc::limits {.bytes = ..., .tasks = ...}) { }` — контекстный оператор
async-тела, как `deadline`. Бюджет вкладывается в прежний бюджет задачи, а выход из блока его
восстанавливает. Каждое выделение runtime, которое делает код задачи, учитывается в бюджете и
его предках и возвращается при освобождении на любом потоке, в том числе после блока. Каждая
R-задача учитывается от запуска до уничтожения, запущенная задача получает бюджет запускающей.
Отказ — `alloc_error::budget_exhausted` или `start_error::budget_exhausted`, для `new` — panic
`allocation_failure`. Учёт ведёт сам аллокатор: шардированная таблица учтённых выделений,
счётчики бюджетов с подсчётом ссылок, флаг отказа на поток. Без бюджетов освобождение не
обращается к таблице. Пример `examples/service` получил режим `repeat`: обработчик строит ответ
под бюджетом `budget_bytes`, отказ на границе освобождает уже построенные строки, и сервис
продолжает работу. Подробности — в разделе 43 [матрицы](language-completeness-matrix.ru.md).

### L35. Ограниченная рекурсия

- [x] **L35.1** Атрибут `@recursion(depth = N)` у синхронных функций рекурсивного цикла;
  превышение глубины бросает `core::recursion_error` до входа в вызов.
- [x] **L35.2** Статический стек учитывает N повторений цикла; async-рекурсия запрещена.

**Готово, когда:** рекурсивный разборщик выражений в примере ограничивает вложенность, а
учёт стека сгенерированного C подтверждает границу.

Выполнено 1 октября (Core draft.91, 493 правила: новое R-FUNC-0026, изменены R-FUNC-0004,
R-GRAM-0007 и таблица диагностик; Library draft.48, 369 правил: `core::recursion_error` в
R-LIB-0001 и в списке стандартных ошибок R-SLIB-GEN-0002). `@recursion(depth = N)` с N от 1 до
65535 ставится на синхронную функцию с телом, которая объявляет `core::recursion_error`. На
каждом потоке существует не более N активаций функции, каждый экземпляр generic-функции считает
свои; вызов сверх границы бросает `core::recursion_error {.depth = N}` до выполнения тела,
аргументы уничтожаются, как при любом throw. Цикл графа вызовов допустим, только если каждая его
функция несёт атрибут; цикл через любую другую функцию, значение функции, dyn, хук, initializer
`call_once` или async-запуск по-прежнему R-DIAG-STACK-001, поэтому async-рекурсии нет. Граница
стека точки входа учитывает N кадров каждой функции рекурсивного множества:
`tools/compute_stack_entries.py` читает метки `R_STACK_RECURSION` сгенерированного C. Пример
`calculator` получил команду `eval` — рекурсивный разборщик выражений с `@recursion(depth = 16)`:
глубже 16 уровней скобок — `expression nests deeper than 16 levels`, а заголовок стека сборки
подтверждает 16 кадров каждой из трёх функций. Подробности — в разделе 44
[матрицы](language-completeness-matrix.ru.md).

Решение владельца (2 октября 2026), после завершения программы: SQLite, которую вызывает
`std.sqlite`, собирается из исходников вместе с библиотекой, а не берётся из системы (M33), и
в `std.fs` добавляется то, на чём стоят атомарный коммит, доступ к файлу из нескольких процессов
и журналы упреждающей записи: блокировки, чтение и запись по смещению, сброс на носитель с
выбором гарантии и отображение файла в память (M34).

### M33. SQLite из исходников

- [x] **M33.1** Amalgamation SQLite 3.53.4 с проверенным SHA3-256, статическая сборка с
  параметрами библиотеки вместо системной libsqlite3; правило Annex C о версии и параметрах

Выполнено 2 октября (Library draft.54, 420 правил: новое R-SLIB-IDB-0017, изменена
R-SLIB-SQLITE-0001; Core draft.93 не менялась). Системная libsqlite3 macOS — сборка Apple

### M34. Файлы: блокировки, позиционный ввод-вывод, долговечность, отображение

- [x] **M34.1** Блокировки файлов: разделяемая и исключительная, на весь файл и на диапазон
  байтов, попытка без ожидания и ожидание со сроком и отменой.
- [x] **M34.2** Чтение и запись по смещению без общей позиции файла, в том числе в
  заимствованные буферы.
- [x] **M34.3** Сброс на носитель с выбором гарантии: барьер порядка записи (`F_BARRIERFSYNC`),
  передача устройству (`fsync`) и полный сброс кэша накопителя (`F_FULLFSYNC`).
- [x] **M34.4** Отображение файла в память: только чтение и разделяемая запись, синхронизация
  отображения с файлом. Модуль на R не мог вернуть view чужой памяти, привязанный к объекту
  отображения (срез из сырых частей получал регион локальной переменной, R-UNSAFE-0008);
  владелец выбрал примитив Core со «якорем» региона (L38), на нём отображение и сделано.

**Готово, когда:** пример держит файл данных с журналом, которым несколько процессов пользуются
по очереди под блокировкой, пишет по смещениям и переживает обрыв между записью журнала и
данных.

Выполнено 2 октября для M34.1–M34.3 (Library draft.55, 424 правила: новые R-SLIB-FS-0014..0016
и R-SLIB-IDB-0018, изменены R-SLIB-ASYNC-0011 и R-SLIB-IDB-0006; Core draft.93 не менялась).
`std.fs::sync` с уровнями `barrier`, `device` и `media`; `read_at`, `write_all_at` и их
scoped-формы `read_at_into` и `write_all_at_from`, которые занимают очередь общей позиции, но не
меняют её; `try_lock`, `lock` и `unlock` на блокировках открытого файла (`F_OFD_SETLK`), где
`lock` ждёт повторными попытками по таймеру, не занимая потоков файловой очереди. Пример
`journal` — записи фиксированного размера с журналом упреждающей записи. Подробности — в
разделе 52 [матрицы](language-completeness-matrix.ru.md).

Выполнено 2 октября для M34.4 вместе с L38 (Library draft.57, 426 правил: новые
R-SLIB-FS-0017 и R-SLIB-IDB-0019, изменена R-SLIB-RSRC-0002). `std.fs` получила R-часть:
`unsafe std.fs::map_file` отображает диапазон файла на пуле блокирующих вызовов через нативный
провайдер `std.fs.native` (`mmap` с `MAP_SHARED`), `std.fs::mapping` держит страницы через

(`msync`) удерживает страницы до своего завершения. Пример `journal` читает записи командой
`scan` через отображение и воспроизводит журнал в `recover` через отображение для записи.

### L38. Срезы, привязанные к объекту

Решение владельца (2 октября 2026): «Расширить ядро ... Новый unsafe-примитив „срез из сырого
указателя, привязанный к объекту“ — да, но только сразу пересмотри все другие вещи, где это
пригодится, и сразу переделывай».

- [x] **L38.1** `unsafe core::slice_from_raw_parts_in(anchor, pointer, length)` и
  `core::slice_from_raw_parts_in_mut`: тот же дескриптор, что у `core::slice_from_raw_parts`,
  но с регионом якоря — заимствования, среза или `str` (для изменяемой формы —
  исключительного), а не свежим регионом получателя. Якорь не вычисляется, поэтому он —
  место или заимствование места; срез можно вернуть и хранить там же, где заимствование от
  якоря, а правила заимствования держат якорь живым, неподвижным и (для изменяемой формы)
  неиспользуемым, пока жив срез.
- [x] **L38.2** Приведение nullable сырого указателя к nullable сырому указателю другого типа
  или константности (null остаётся null); приведение nullable к non-null по-прежнему отвергается.
- [x] **L38.3** Обзор мест, где примитив нужен, и переделка: `std.tls::stream<S>::protocol`
  возвращает `str` — view имени ALPN в конфигурации, без копии и выделения памяти; пример
  `c_bridge` пишет и читает пакет через срезы, привязанные к `std.c::handle`, и смотрит на байты
  как на `c_char` через срез, привязанный к ним; M34.4 (`std.fs::mapping`). Оставлены как есть
  с обоснованием: встроенные `std.c::c_string`, `std.secret::buffer`, `std.string`/`std.format`
  (их представление разделено с runtime), `std.slice::swap` (два непересекающихся
  исключительных среза одного объекта), байты столбцов `std.sqlite` (память SQLite живёт до
  следующего шага оператора, а строки уходят из потока пула).
- [x] **L38.4** Найденный при обзоре дефект L38-1: выполнения одного подготовленного оператора
  `std.sqlite` из параллельных задач перемежали свои bind и step на потоках пула; теперь
  выполнения оператора идут по очереди под его мьютексом (R-SLIB-SQLITE-0007). Текст столбца
  больше не копируется дважды.

**Готово, когда:** библиотечный модуль на R возвращает view памяти нативного объекта из метода
этого объекта, а компилятор отвергает его перемещение, drop и конфликтующее использование, пока
view жив.

Выполнено 2 октября (Core draft.94, 495 правил: изменены R-UNSAFE-0008 и R-EXPR-0019; Library
draft.56 — изменена R-SLIB-TLS-0004, затем draft.57 вместе с M34.4). Подробности — в разделе
53 [матрицы](language-completeness-matrix.ru.md).

### P4.1. Скорость ввода-вывода и разбора

Решение владельца (2 октября 2026): «реализуем» — блок производительности из плана фундамента
(§22.2, §22.10), первая часть направления P4 раздела 7.

- [x] **P4.1.1** Файлы без канала Dispatch I/O на операцию: адаптер файловых передач

- [x] **P4.1.2** Сокеты: неблокирующий вызов при активации и источники готовности на хэндле.

описывают новый механизм и батарея проходит. Ориентиры плана фундамента: чтение 4 КиБ — около

Выполнено 3 октября (Core draft.96, 496 правил: новый R-TERM-0016; Library draft.61, 440 правил:

блокирующих файловых передач в первом варианте), P4.1-3 и P4.1-4 (побайтовое заполнение
`std.alloc::bytes` и обход элементов при уничтожении массива), P4.1-5 (`std.service` терял исход
обработчика или запрос остановки, отменяя проигравший приём в `select`; был и до этапа), P4.1-6
и P4.1-7 (тот же шаблон в потоке подписки `std.mcp` и в примере `ipc`), P4.1-8 (рантайм позволял
завершению заменить уже выбранную отмену, и ожидающего подтверждали дважды). Для `std.deflate` осталась
поэлементная инициализация таблиц сжатия: нужна операция `std.array`, создающая массив
заданной длины, — это новая публичная операция и решение владельца (сделана на этапе P4.2).

### P4.3. Доказательство границ и `std.deflate` уровня zlib

Решение владельца (3 октября 2026): «делаем два дешевых исправления / алгоритм уровня зип / и
главное - ... если мы знаем что переполнения не достижимо мы вызваем фаст функцию» — ответ на
вопрос, что держит `std.deflate` в 3,24× от zlib после P4.2.

- [x] **P4.3.1** Компилятор: индекс, доказанно меньший границы, генерируется без проверки
  (R-EXPR-0021); доказательство — проход по HIR синхронного тела с фактами о локальных
  объектах и длинах срезов и `array<T>`, плюс диапазоны значений без фактов везде, включая
  асинхронные кадры.
- [x] **P4.3.2** Тем же доказательством снимаются проверки сужающих `as` (R-EXPR-0015).
- [x] **P4.3.3** Два дешёвых исправления `std.deflate`: куча при построении кодов Хаффмана и
  запись одноразовых `inflate`/`deflate` прямо в результат без поэлементного `push`.
- [x] **P4.3.4** Распаковка уровня zlib: таблицы быстрого декодирования, быстрый цикл по
  образцу `inflate_fast`, окно раз в вызов, блочное копирование совпадений и хранимых
  блоков, векторизуемый Adler-32, CRC-32 срезами по 8 байт.
- [x] **P4.3.5** Сжатие уровня zlib: цепочки `u16`, токенизация на локальных переменных,
  вставка позиций без цепочки зависимостей, `longest_match` на срезах, таблицы кодов длин и
  дистанций; сжатый вывод побайтно прежний.

**Готово, когда:** горячие циклы `std.deflate` генерируются без проверок границ, тесты
показывают, что недоказанные проверки остаются и паникуют, вывод сжатия не меняется,
раунд `std.deflate` заметно ближе к zlib, батарея проходит.

Выполнено 3 октября (спецификации без изменений: Core draft.96, 496 правил; Library draft.62,
440 правил; снятие проверки — оптимизация по R-AM-0003). Раунд `std.deflate` 0,34 → 0,085 мс,
3,24× → 1,19× от zlib; сжатый вывод побайтно прежний. В примере `assistant` проверок границ
729 → 562. Дефект P4.3-1 (одноразовый `inflate` не читал конец блока при заполненном выходе).
Подробности — в разделе 58 [матрицы](language-completeness-matrix.ru.md).

### P4.4. Проверки — в статический анализ

Решение владельца (3 октября 2026): «Производительность (P4), что ещё далеко от C / давай это
реализуем и найдем еще провалы по оптимизации - делаем упор на мысль о том что как нам вывести
проверки в статический анализ кода».

- [x] **P4.4.1** Проверка переполнения знаковых `+` и `-` — по знаку результата
  (`((r ^ результат) & (l ^ результат)) < 0`), умножения до 32 бит — в 64-битном произведении,
  64-битного умножения — быстрым путём, когда оба множителя умещаются в 32 бита.
- [x] **P4.4.2** `await f(...)` асинхронной функции, которая доказанно не приостанавливается

- [x] **P4.4.3** `await receiver.receive()` при непустом или закрытом канале завершается сразу,
  без внешней задачи и перехода через GCD.
- [x] **P4.4.4** Индексы вида `A + k·S` во внутреннем цикле `for (...; k < B; k += 1)`
  проверяются один раз до цикла; если проверка проходит, работает копия цикла без этих
  проверок, иначе — цикл как написан.
- [x] **P4.4.5** Разыменование `own` — чтение поля без вызова рантайма.
- [x] **P4.4.6** Найденные провалы: измерены новые ядра (`matrix_mul`, `channel_stream`,

### Требования игрового сервера и решение владельца от 4 октября 2026

Владелец спросил, чего не хватает языку для сервера мобильной игры: около 120 HTTP-маршрутов,
модели поверх PostgreSQL, токены JWT с подписью ES256, шифрованный протокол на AES-128-CBC,
проверка покупок Google Play и загрузка конфигурации из Google Sheets через OAuth2 сервисного
аккаунта; сервер работает под Linux в контейнере.

Вывод разбора: сам язык такой сервер выражает. Не хватает цели Linux (направление P1 раздела 7),
криптографии с открытым ключом и AES-CBC, системных корней TLS, JWT и OAuth2, часовых поясов,
типизированной конфигурации, типов и отображения строк PostgreSQL, раскрутки паники и
middleware HTTP, которые могут ждать базу и передавать значения запроса дальше.

Решение владельца (4 октября 2026): «Без этого сервер не запустить - реализовываем 2, 3, 4, 5 /
Серьёзные пробелы, которые можно обойти - тоже реализовываем / JWT и OAuth2-клиента нет ...
добавляем». Пункт 1 разбора, цель Linux, в решение не вошёл и остаётся направлением P1.
Этапы M36–M42 и L39 выполняются по правилу раздела 8, порядок задаёт таблица раздела 4:
раскрутка паники идёт перед middleware, потому что сервер должен превращать панику обработчика
в ответ 500.

### Повторный разбор требований и решение владельца от 5 октября 2026

После M36–M41 владелец попросил проверить ещё раз, чего не хватает такому серверу, кроме цели
Linux. Три независимых разбора (HTTP-слой, база и фоновая работа, внешние сервисы) нашли:
около 200 маршрутов в нескольких группах; цепочки middleware с проверкой ES256 и сессии в базе,
шифрованием тела запроса и ответа AES-CBC и обёрткой команды клиента, которая выполняет
обработчик внутри транзакции с `SELECT … FOR UPDATE`, передаёт ему соединение транзакции и
сохраняет ответ для повторной выдачи; работу с базой через отображение объектов (неявный upsert
при сохранении, пакетные вставки, загрузка связанных записей, вложенные транзакции через
SAVEPOINT); журнал в JSON с именами полей, по которым его разбирает сборщик журналов, и отправку
записей об ошибках во внешний сервис.

Решение владельца (5 октября 2026): «Блокеры, которые уже в плане — давай реализовывать» (L39 и M42
в расширенном объёме; имя cookie сессии относится к приложению и в язык не входит — в `std.http`
нужен общий разбор cookie); журнал с заданными именами полей — «обязательно» (этап M44); отправка
ошибок во внешний сервис — внешний плагин, не стандартная библиотека, в работу не входит; «мелочи
совместимости — давай» (в M42 и M44). На вопрос, почему нельзя сделать отображение объектов на
таблицы, ответ: можно — не на рефлексии времени выполнения, которой в R нет, а на схеме типа времени
трансляции (`std.json::schema::<T>()`, атрибуты `@json`, обобщённые функции), на которой уже
построено отображение M41; размещение (стандартная библиотека или внешний пакет) ждёт решения
владельца, этап M43 будет добавлен после него.

6 октября 2026 владелец, разобрав пример с `std.postgres`, попросил: передавать владеющую строку
туда, где ожидается `str`, без `.as_str()` (этап L41); операции, которые выполняют запрос, делать
методами соединения, а не свободными функциями; ввести пользовательские атрибуты (этап L42) и
после них вернуться к M43. L40 выполняется после M43, если владелец не решит иначе.

### L39. Раскрутка паники

- [x] **L39.1** Стратегия unwind на цели (R-ERR-0005): паника в коде R уничтожает
  инициализированные объекты и выполняет `finally` от внутреннего к внешнему; паники внутри
  рантайма на C остаются аварийным завершением (R-ERR-0006).
- [x] **L39.2** Задачи: паника завершает задачу, наблюдаемая паника повторяется в точке `await`,
  ненаблюдаемая уходит в хук паники; операция наблюдения паники задачи без повторения.
- [x] **L39.3** Хук паники для отчёта о сбое: категория, сообщение, место в исходном тексте.
- [x] **L39.4** Проверки: освобождение ресурсов при панике (файлы, сокеты, блокировки, `arc`),
  вторая паника, паника в `finally`, группы задач, отмена; стоимость на тестах производительности.

**Готово, когда:** паника в одной задаче не завершает процесс, ресурсы освобождаются, а
наблюдаемое поведение без паники не меняется.

Выполнено 5 октября (Core draft.97, 496 правил — изменились только номера interface schema в
тексте; Library draft.65, 468 правил: новое R-SLIB-ASYNC-0020; interface schema 32; манифесты целей —
ревизия 10, у hosted-цели `panic.strategy` = `unwind`). Паника в коде R раскручивается явным
распространением: живые объекты уничтожаются, `finally` выполняются, задача завершается паникой,
`await` повторяет её, `await std.async::join(move t)` наблюдает её как
`std.thread::join_result<T>`, поток — `panicked` в `join_result`, scoped-поток —
`scoped_thread_panic` родителю, ненаблюдаемый отчёт уходит в хук рантайма (строка с категорией,
местом и сообщением). Программный приёмник отчётов для журнала перенесён в M44. Пример `offload`
получил команду `fault`. Подробности, решения и дефекты L39-1..L39-12 — в разделе 66 матрицы.

План реализации (5 октября 2026, решения записываются в матрицу по ходу этапа):

- Механизм — явное распространение без setjmp/longjmp и без исключений платформы: рантайм
  держит состояние паники потока (категория, место, текст до 256 байт, фаза «распространяется»
  или «очистка») и глобальный счётчик потоков с распространяющейся паникой, по которому
  сгенерированный код проверяет панику одной загрузкой и переходом. Паника внутри C-кода
  рантайма и библиотеки по-прежнему аварийная (R-ERR-0006).
- Семантика строит для каждого узла, который может паниковать, выход при панике — точный список
  сброса активных символов, как у непойманной проверяемой ошибки; одинаковые списки подряд
  разделяются. Эмиттер ставит проверку после вызова или после места паники и уходит по этому
  выходу через `finally` с новой причиной отложенного завершения «паника»; функция возвращается к
  вызывающей, и проверка повторяется там.
- Асинхронные функции: проверка после инструкций MIR, активные `finally` выполняются, шаг
  возвращает новый статус «паника», локальные сбрасывает деструктор кадра, как при отмене.
- Границы: `main` после раскрутки печатает отчёт и завершает процесс аварийно (R-ERR-0009);
  задача завершается паникой, `await` повторяет её, ненаблюдаемая уходит в хук; поток — в
  `panicked` его `join_result`; паника, дошедшая до C-обёртки обратного вызова, — аварийно.
- Проверки после вызовов функций, которые не могут паниковать (по графу вызовов), опускаются;
  стоимость меряется на тестах производительности.

### L40. Деструктуризация структур и исходов

Добавлен 4 октября 2026 при выполнении M37 (дефект M37-1). Каталог `std.fs` обходится
операцией `next`, которая возвращает итератор внутри полезной нагрузки
`entry { iterator; entry; }`. Забрать поле из этой нагрузки в R нельзя: `move` требует целого
объекта (R-OWN-0005), а `match` не разбирает непрозрачные исходы стандартной библиотеки
(R-EXPR-0031). Поэтому программа на R видит только первую запись каталога. Та же беда у
`std.fs::write_file_result::failed { error; data; }`: данные для повтора записи не достать.

- [x] **L40.1** Объявление `auto {.поле = имя, ...} = move значение;` для структур без
  пользовательского `drop` и для полезных нагрузок исходов с именованными полями: значение
  поглощается целиком, каждое поле переходит в новую локальную переменную.
- [x] **L40.2** Полный обход каталога в `std.fs` и пример; `SSL_CERT_DIR` в
  `std.tls::system_client_config`.

**Готово, когда:** программа на R перечисляет все записи каталога и повторяет неудавшуюся
атомарную запись с возвращёнными данными.

Выполнено 7 октября 2026 по решению владельца («делаем») вместе с M45 (Core draft.102, 498
правил: изменено R-STMT-0022, грамматика Annex A — 303 продукции; Library draft.72, 477 правил:
изменено R-SLIB-TLS-0007). Пример `workspace` перечисляет каталог командой `entries`, фикстура

  `narrowing_div_SUFFIX` для беззнаковых, результат — кортеж; форма без суффикса выбирает тип по
  операндам; узкое деление вне области — panic `division_by_zero` или `integer_overflow`.
- [x] **L45.2** Вычисление при трансляции (Core R-FUNC-0023).
- [x] **L45.3** C17: переносимые идиомы строгого C17, замер выбранных инструкций и цены.
- [x] **L45.4** Фикстуры, пример `numbers` (все операции всех типов против Python), команды `bits`
  и `wide` примера `binary`.

**Готово, когда:** операции доступны во всех профилях, совпадают при трансляции и при
выполнении, а замер показывает, во что их превращает закреплённый компилятор C.

Выполнено 7 октября 2026 (Library draft.74, 478 правил: новое R-LIB-0027, inventory 1580
записей; Core draft.104, 500 правил: изменено R-FUNC-0023). Подробности — в разделе 76 матрицы.

### L46. Помеченный `switch` и `continue метка (значение)`

Добавлен 7 октября 2026 по решению владельца («2 делаем»). Цикл интерпретатора, лексер и разбор
протокола — машины состояний: `while (true) { switch (state) { ... } }` с отдельной переменной
состояния и `break` из `switch`, который не выходит из цикла. Нужна запись, в которой клауза сама
выбирает следующую.

- [x] **L46.1** Core R-STMT-0024: `name: switch (value) { ... }` над целым, `char` или enum без
  полей (программы или библиотеки); `continue name (next);` выбирает и выполняет клаузу для нового значения,
  `break name;` выходит из `switch`, завершившаяся клауза выходит как прежде; `continue;` без
  метки относится к циклу вокруг `switch`.
- [x] **L46.2** Анализ состояний объектов как у цикла: клауза, выбранная снова, видит состояния
  из каждого выбора; вычисление при трансляции.
- [x] **L46.3** C17 и замер: размноженная диспетчеризация против обычного цикла и computed goto.
- [x] **L46.4** Фикстуры (синхронная, асинхронная, отказы) и команда `rpn` примера `calculator`.

**Готово, когда:** машина состояний пишется помеченным `switch`, перемещение значения между
выборами отвергается как в цикле, а решение о C17 опирается на замер.

Выполнено 7 октября 2026 (Core draft.105, 501 правило: новое R-STMT-0024, изменено R-STMT-0004, в
грамматике Annex A новая продукция `labeled-switch-statement`, всего 306). Подробности — в
разделе 77 матрицы.

## 6. Условный следующий уровень языка

Эти направления сохраняются в очереди; они не расширяют автоматически принятый объём.
26 сентября 2026 владелец решил реализовать их этапами L15–L18 (раздел 5).

- **G1. Параметризованные associated types.** Сначала описать конкретные lending
  iterator, view или decoder API, которым не хватает существующих средств.
  Проверить, достаточно ли параметров типа/константы либо требуется зависимость
  результата от региона конкретного вызова. После этого проектировать собственные
  параметры associated types, bounds, подстановку и проверку определений. Пример L14.6:
  lending-итератор, чей элемент — view буфера итератора, R-TYPE-0045 отвергает; обычный
  метод с последовательным использованием выражается.
- **G2. Более сложные регионные контракты.** Сначала собрать случаи, которые не
  выражаются текущими покомпонентными inferred origins. Явные lifetime-параметры
  не являются заранее принятым решением. Примеры L14.6: результат функции, зависящий только
  от того, что держит аргумент (декодер, generic-помощник с `I*`); запись view-параметра в
  контейнер другого параметра; владелец (`own T*`), чья полезная нагрузка держит view.
- **G3. Прочие generics-пробелы из прежней очереди.** Гетерогенные пакеты типов
  (M15) и вывод по ожидаемому результату остаются последующими предложениями.
  Result-only generics и явное закрытие generic-функций перенесены в принятый L8.
  Примеры L14.6: `std.array::create()` без явного аргумента типа, `@generic<T...>`.

## 7. Сохранённая очередь вне языкового этапа

## 8. Правило выполнения одной задачи

1. Сценарий и семантическое решение; нормативный английский текст и русский перевод.
2. Вертикальная реализация через parser → semantic → HIR/MIR → C17 с metadata,
   проверкой ресурсов и cleanup там, где они затронуты.
3. Позитивные и негативные проверки контракта, исполняемый пример и релевантные
   проверки взаимодействий. Сборка без предупреждений; warnings-as-errors сохраняется.

   поддержку принятого контракта по всему пути, а не только принятый синтаксис.

итоговая L6. Матрица пробелов L0
пополняется по мере реализации. L3 исключён.
